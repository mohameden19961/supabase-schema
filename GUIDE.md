du projet à l'automatisation des migrations via CI/CD, en passant par la sécurité
niveau ligne (RLS) et les relations entre tables.

## 2. Installation du CLI Supabase

```bash
# Option A : via npm
npm install -g supabase

# Option B : binaire officiel (recommandé)
curl -fsSL https://github.com/supabase/cli/releases/latest/download/supabase_linux_amd64.tar.gz | tar -xz
sudo mv supabase /usr/local/bin/

# Vérification
supabase --version
```

## 3. Initialisation du projet Supabase

```bash
supabase init
```

Crée la structure locale :
```
supabase/
├── config.toml       # Configuration du projet
└── migrations/       # Dossier des migrations SQL
```

Le fichier `config.toml` contient les réglages du projet (port, auth, stockage…).
L'identifiant du projet (`project_id`) est dérivé du nom du dossier.

## 4. Connexion CLI au compte Supabase

```bash
supabase login
```

Un lien s'ouvre dans le navigateur. Après authentification, un token CLI est
créé et stocké localement. Vous êtes maintenant connecté.

Pour les environnements headless (CI/CD), utilisez plutôt un **Personal Access
Token** depuis `supabase.com/dashboard/account/tokens`.

## 7. Première migration : table todos

```bash
supabase migration new create_todos_table
```

Un fichier `supabase/migrations/<timestamp>_create_todos_table.sql` est créé.
Éditez-le :

```sql
create table todos (
  id bigint generated by default as identity primary key,
  title text not null,
  is_done boolean default false,
  created_at timestamptz default now()
);

alter table todos enable row level security;

create policy "Allow all access to todos"
on todos for all
using (true)
with check (true);

insert into todos (title, is_done) values
  ('Apprendre Supabase CLI', true),
  ('Connecter GitHub à Supabase', true),
  ('Créer une migration', false),
  ('Comprendre RLS', false);
```

Appliquez la migration :

```bash
supabase db push
```

Le CLI compare l'état local avec l'état distant et applique seulement les
migrations manquantes, dans l'ordre.

## 9. Migration : RLS basé sur l'authentification

Jusqu'ici la politique RLS permettait à tout le monde de tout faire. Cette
migration ajoute une colonne `user_id` liée à `auth.users` et remplace les
politiques par des règles basées sur l'utilisateur connecté.

```bash
supabase migration new add_auth_to_todos
```

```sql
alter table todos
add column user_id uuid references auth.users(id) default auth.uid();

drop policy "Allow all access to todos" on todos;

create policy "Users can view their own todos"
on todos for select
using (auth.uid() = user_id);

create policy "Users can insert their own todos"
on todos for insert
with check (auth.uid() = user_id);

create policy "Users can update their own todos"
on todos for update
using (auth.uid() = user_id);

create policy "Users can delete their own todos"
on todos for delete
using (auth.uid() = user_id);
```

```bash
supabase db push
```

Chaque utilisateur ne voit et ne modifie que ses propres tâches. La fonction
`auth.uid()` est fournie par Supabase Auth.

## 11. Migration : table todo_comments (one-to-many)

Relation N:1 entre `comments` et `todos`.

```bash
supabase migration new create_todo_comments_table
```

```sql
create table todo_comments (
  id bigint generated by default as identity primary key,
  todo_id bigint not null references todos(id) on delete cascade,
  content text not null,
  created_at timestamptz default now()
);

create index idx_todo_comments_todo_id on todo_comments(todo_id);

alter table todo_comments enable row level security;

create policy "Public read access to comments"
on todo_comments for select
using (true);

create policy "Public insert access to comments"
on todo_comments for insert
with check (true);

insert into todo_comments (todo_id, content) values
  (1, 'CLI installée avec succès'),
  (1, 'Testé login et init sans problème'),
  (2, 'Connexion GitHub validée dans le dashboard'),
  (3, 'Première migration créée et appliquée');
```

Points clés :
- `REFERENCES todos(id) ON DELETE CASCADE` → supprimer un todo supprime ses commentaires
- L'index sur `todo_id` accélère les requêtes par todo parent
- RLS en lecture seule publique (pour l'apprentissage)

```bash
supabase db push
```

## 12. Migration : tables tags + todo_tags (many-to-many)

Relation N:N entre `todos` et `tags`, via une table de jonction.

```bash
supabase migration new create_tags_and_todo_tags
```

```sql
create table tags (
  id bigint generated by default as identity primary key,
  name text not null unique,
  color text default '#6b7280'
);

create table todo_tags (
  todo_id bigint not null references todos(id) on delete cascade,
  tag_id bigint not null references tags(id) on delete cascade,
  primary key (todo_id, tag_id)
);

create index idx_todo_tags_todo_id on todo_tags(todo_id);
create index idx_todo_tags_tag_id on todo_tags(tag_id);

alter table tags enable row level security;
alter table todo_tags enable row level security;

create policy "Public read access to tags"
on tags for select
using (true);

create policy "Public read access to todo_tags"
on todo_tags for select
using (true);

create policy "Public insert access to tags"
on tags for insert
with check (true);

create policy "Public insert access to todo_tags"
on todo_tags for insert
with check (true);

insert into tags (name, color) values
  ('CLI', '#3b82f6'),
  ('GitHub', '#10b981'),
  ('Database', '#f59e0b'),
  ('Urgent', '#ef4444');

insert into todo_tags (todo_id, tag_id) values
  (1, 1), (1, 3),
  (2, 2),
  (3, 3),
  (4, 3), (4, 4);
```

```bash
supabase db push
```

## 13. CI/CD avec GitHub Actions

### a. Générer un token Supabase

1. Aller sur [supabase.com/dashboard/account/tokens](https://supabase.com/dashboard/account/tokens)
2. Cliquer sur **Generate new token**
3. Nommer le token (ex: `github-actions`)
4. Copier le token généré

### b. Ajouter le secret sur GitHub

1. `Repo → Settings → Secrets and variables → Actions`
2. **New repository secret**
3. Name : `SUPABASE_ACCESS_TOKEN`
4. Secret : coller le token Supabase

### c. Créer le fichier workflow

`.github/workflows/deploy.yml` :

```yaml
name: Deploy Supabase migrations

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - uses: supabase/setup-cli@v1
        with:
          version: latest

      - run: supabase link --project-ref camkgvkpkhawevpxmxxe
        env:
          SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}

      - run: supabase db push
        env:
          SUPABASE_ACCESS_TOKEN: ${{ secrets.SUPABASE_ACCESS_TOKEN }}
```

### d. Versionner et pousser

```bash
mkdir -p .github/workflows
# créer le fichier ci-dessus
git add .github/workflows/deploy.yml
git commit -m "Add CI/CD workflow for Supabase migrations"
git push
```

### e. Résultat

Chaque `git push` sur `main` déclenche automatiquement :

1. Checkout du code
2. Installation du CLI Supabase
3. Liaison au projet distant (via le token)
4. Application des nouvelles migrations

Plus besoin de lancer `supabase db push` manuellement.

## 14. Nettoyage : fichier binaire commit par erreur

Un binaire `supabase-go` (~97 MB) a été commit accidentellement.

### Suppression simple (le fichier reste dans l'historique)

```bash
git rm supabase-go
echo "supabase-go" >> .gitignore
git add .gitignore
git commit -m "Remove accidentally committed binary"
git push
```

### Purge complète de l'historique (repo encore jeune)

```bash
sudo apt install git-filter-repo
git filter-repo --path supabase-go --invert-paths --force
git remote add origin https://github.com/mohameden19961/supabase-schema.git
git push origin main --force
```

Cette opération réécrit l'historique Git. À faire uniquement sur un repo jeune
ou après accord de l'équipe.

## 15. Résumé du cycle

```
1. supabase migration new <nom>
2. Écrire le SQL (CREATE / ALTER / RLS / policies / data)
3. supabase db push               ← vérification locale (ou CI)
4. git add . && git commit -m "..."
5. git push                       ← déclenche GitHub Actions
6. GitHub Actions applique la migration sur Supabase distant
```

Le cycle est entièrement piloté par le code : le schéma vit dans les fichiers
SQL, pas dans le dashboard Supabase. Cela permet le versionning, la revue de
code, et la reproductibilité.
